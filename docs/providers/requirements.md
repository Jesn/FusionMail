## 1. 业务背景

### 1.1 现状问题

当前 FusionMail 系统存在以下问题：

1. **配置硬编码**
   - 邮箱提供商配置（IMAP 服务器、端口、推荐协议等）硬编码在代码中
   - 新增或修改提供商需要修改代码并重新部署
   - 无法灵活适配不同地区或企业的特殊邮箱服务

2. **OAuth2 配置单一**
   - Gmail、Outlook 等 OAuth2 认证只能配置一个 Client ID/Secret
   - 存在配额限制风险（如 Google API 每日配额）
   - 无法实现负载均衡和配额管理
   - 测试环境和生产环境配置不能隔离

3. **运维困难**
   - 配置变更需要开发人员介入
   - 无法快速响应邮箱服务商的配置调整
   - 缺乏配置管理和监控能力

### 1.2 业务价值

实现配置化后，可以带来以下价值：

1. **灵活性提升**
   - 动态添加、修改、禁用邮箱提供商
   - 支持企业自建邮箱服务
   - 快速适配新的邮箱服务商

2. **可用性增强**
   - OAuth2 多应用配置，避免单点故障
   - 配额管理和自动切换，提升服务可用性
   - 降低 API 限流风险

3. **运维效率**
   - 配置变更无需重新部署
   - 可视化配置管理
   - 实时监控各配置使用情况

4. **成本优化**
   - 合理分配 API 配额
   - 避免超配额产生的额外费用
   - 支持多租户场景

## 2. 功能需求

### 2.1 邮箱提供商配置化

#### 2.1.1 功能描述

将邮箱提供商的配置信息从代码迁移到数据库，支持动态管理。

#### 2.1.2 核心功能

1. **提供商基础配置**
   - 提供商标识（name）：唯一标识，如 gmail、outlook、qq 等
   - 显示名称（display_name）：用户界面显示的名称
   - 支持的协议（supported_protocols）：如 OAuth2、IMAP、POP3
   - 推荐协议（recommended_protocol）：默认选择的协议
   - 是否需要 OAuth（requires_oauth）：标识是否强制使用 OAuth2

2. **服务器配置**
   - IMAP 服务器地址和端口
   - POP3 服务器地址和端口
   - SMTP 服务器配置（预留）

3. **管理功能**
   - 启用/禁用提供商
   - 排序顺序（影响前端显示顺序）
   - 描述信息

#### 2.1.3 用户故事

**US-001: 作为系统管理员，我希望在数据库中配置邮箱提供商，以便快速添加新的邮箱服务**

- **场景**: 公司需要添加企业邮箱支持
- **前置条件**: 管理员已登录系统
- **操作步骤**:
  1. 进入提供商管理页面
  2. 点击"添加提供商"
  3. 填写提供商信息（名称、IMAP 配置等）
  4. 保存配置
- **预期结果**:
  - 配置保存成功
  - 用户添加账户时可以选择新的提供商
  - 系统自动使用新配置连接邮箱服务

**US-002: 作为系统管理员，我希望修改提供商的服务器配置，以适应邮箱服务商的变更**

- **场景**: QQ 邮箱更换了 IMAP 服务器地址
- **前置条件**: 管理员已登录系统
- **操作步骤**:
  1. 进入提供商管理页面
  2. 找到 QQ 邮箱配置
  3. 修改 IMAP 服务器地址
  4. 保存更改
- **预期结果**:
  - 配置更新成功
  - 现有 QQ 邮箱账户自动使用新配置
  - 新添加的 QQ 账户使用新配置

**US-003: 作为系统管理员，我希望临时禁用某个提供商，以应对服务异常**

- **场景**: 163 邮箱服务出现故障，暂时无法使用
- **前置条件**: 管理员已登录系统
- **操作步骤**:
  1. 进入提供商管理页面
  2. 找到 163 邮箱配置
  3. 关闭"启用"开关
  4. 保存更改
- **预期结果**:
  - 用户添加账户时不再显示 163 邮箱选项
  - 现有 163 账户暂停同步
  - 故障恢复后可重新启用

### 2.2 OAuth2 多客户端配置

#### 2.2.1 功能描述

支持为同一个邮箱提供商（如 Gmail、Outlook）配置多个 OAuth2 应用，实现配额管理、负载均衡和环境隔离。

#### 2.2.2 核心功能

1. **OAuth2 客户端配置**
   - 配置名称：便于识别的名称（如"Gmail 生产环境"、"Gmail 测试"）
   - Client ID / Client Secret：OAuth2 应用凭证
   - Redirect URI：回调地址
   - Scopes：权限范围
   - 描述和标签：便于分类管理

2. **配置管理**
   - 默认配置：标记为默认的配置优先使用
   - 优先级：多个配置按优先级排序
   - 启用/禁用：动态开关配置

3. **配额管理**
   - 每日配额限制：设置单个配置的每日使用上限
   - 配额使用追踪：实时记录已使用配额
   - 自动切换：配额超限时自动切换到其他可用配置
   - 配额重置：每日自动重置配额计数

4. **统计监控**
   - 授权次数统计：总次数、成功次数、失败次数
   - 最后使用时间：记录配置的使用情况
   - 可用性状态：显示配置是否可用

5. **用户选择**
   - 自动选择：系统自动选择可用的配置（默认）
   - 手动选择：用户可以选择使用哪个配置
   - 智能推荐：根据配额和可用性推荐最佳配置

#### 2.2.3 用户故事

**US-004: 作为系统管理员，我希望配置多个 Gmail OAuth2 应用，以避免单一配额限制**

- **场景**: 系统用户量增长，单个 Google API 配额不足
- **前置条件**: 管理员已在 Google Cloud Console 创建多个 OAuth2 应用
- **操作步骤**:
  1. 进入 OAuth2 客户端管理页面
  2. 点击"添加配置"
  3. 选择提供商（Gmail）
  4. 填写 Client ID、Client Secret
  5. 设置每日配额（如 1000 次）
  6. 设置优先级
  7. 保存配置
  8. 重复步骤添加多个配置
- **预期结果**:
  - 所有配置保存成功
  - 系统自动在多个配置间分配负载
  - 单个配置配额用完时自动切换

**US-005: 作为普通用户，我希望在添加 Gmail 账户时，系统自动选择可用的 OAuth2 配置**

- **场景**: 用户添加新的 Gmail 账户
- **前置条件**: 系统已配置多个 Gmail OAuth2 应用
- **操作步骤**:
  1. 进入添加账户页面
  2. 选择提供商（Gmail）
  3. 选择协议（OAuth2）
  4. 点击"通过 Google 授权"按钮
- **预期结果**:
  - 系统自动选择配额未超限的配置
  - 跳转到 Google 授权页面
  - 授权成功后账户添加完成
  - 系统记录使用的配置 ID

**US-006: 作为高级用户，我希望手动选择使用哪个 OAuth2 配置，以便使用特定环境的配置**

- **场景**: 开发人员测试时希望使用测试环境的配置
- **前置条件**: 系统配置了多个 Gmail OAuth2 应用（生产、测试、开发）
- **操作步骤**:
  1. 进入添加账户页面
  2. 选择提供商（Gmail）
  3. 选择协议（OAuth2）
  4. 在"OAuth2 配置"下拉框中选择"Gmail 测试环境"
  5. 点击授权按钮
- **预期结果**:
  - 使用选定的测试配置进行授权
  - 显示配置的详细信息（配额使用情况）
  - 授权成功后记录使用的配置

**US-007: 作为系统管理员，我希望监控各 OAuth2 配置的使用情况，以便优化配置分配**

- **场景**: 管理员需要了解各配置的负载情况
- **前置条件**: 系统已配置多个 OAuth2 应用并有一定使用量
- **操作步骤**:
  1. 进入 OAuth2 客户端管理页面
  2. 查看配置列表
  3. 查看各配置的统计数据
- **预期结果**:
  - 显示每个配置的授权次数、成功率
  - 显示配额使用情况（已用/总量）
  - 显示最后使用时间
  - 识别负载不均或异常的配置

**US-008: 作为系统管理员，我希望设置 OAuth2 配置的每日配额，避免超过服务商限制**

- **场景**: Google API 每日免费配额为 10,000 次
- **前置条件**: 管理员已添加 Gmail OAuth2 配置
- **操作步骤**:
  1. 编辑 Gmail OAuth2 配置
  2. 设置每日配额为 9,000（留有余量）
  3. 保存配置
- **预期结果**:
  - 配额设置生效
  - 当日使用达到 9,000 次后，该配置标记为不可用
  - 系统自动切换到其他可用配置
  - 次日凌晨自动重置配额计数

## 3. 非功能需求

### 3.1 性能需求

- **响应时间**: 提供商配置查询 < 100ms
- **并发处理**: 支持 100+ 并发用户同时添加账户
- **缓存策略**: 提供商配置缓存 1 小时，减少数据库查询

### 3.2 安全需求

- **敏感信息加密**: OAuth2 Client Secret 必须加密存储
- **权限控制**: 仅管理员可以管理提供商和 OAuth2 配置
- **审计日志**: 记录所有配置变更操作
- **防止泄露**: API 返回数据不包含 Client Secret

### 3.3 可用性需求

- **降级策略**: 数据库查询失败时使用代码中的默认配置
- **配额保护**: 配额超限时自动切换，不影响用户使用
- **配置验证**: 新增配置时验证格式和连接性

### 3.4 兼容性需求

- **向后兼容**: 现有账户无需迁移，自动适配新配置
- **数据迁移**: 提供脚本将硬编码配置迁移到数据库
- **API 兼容**: 前端 API 接口保持兼容

### 3.5 可维护性需求

- **日志完善**: 记录配置使用、切换、异常情况
- **文档完善**: 提供管理员操作手册

## 6. 风险评估

### 6.1 技术风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 数据迁移失败 | 高 | 低 | 充分测试迁移脚本；提供回滚方案 |
| 配置切换逻辑复杂 | 中 | 中 | 详细设计切换逻辑；充分测试边界情况 |
| 缓存一致性问题 | 中 | 低 | 使用 Redis 统一缓存；配置变更时清除缓存 |
| OAuth2 配额计算不准确 | 高 | 中 | 使用数据库事务保证计数准确；定期校验 |

### 6.2 业务风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 用户体验变化 | 中 | 低 | 保持 UI 一致；提供配置选择提示 |
| 现有账户受影响 | 高 | 低 | 保证向后兼容；充分测试现有功能 |
| 配置管理复杂度增加 | 低 | 高 | 提供管理界面；完善操作文档 |

## 8. 附录

### 8.1 术语表

| 术语 | 定义 |
|------|------|
| Provider | 邮箱提供商，如 Gmail、Outlook、QQ 邮箱等 |
| OAuth2 Client | OAuth2 应用配置，包含 Client ID 和 Client Secret |
| Quota | 配额，指 API 调用次数限制 |
| Priority | 优先级，用于确定多个配置的使用顺序 |
| Fallback | 降级，指系统在主要功能不可用时使用的备用方案 |
