## 邮件列表与详情接口优化需求说明（草案）

> 说明：本需求文档基于当前实现与你的设想整理，侧重保证接口轻量化，同时兼顾用户体验与扩展性。

---

## 一、背景说明

- 当前邮件列表页地址：`http://localhost:4444/inbox`
- 列表数据接口：`GET http://localhost:3333/api/v1/emails?is_archived=false&is_deleted=false&page=1&page_size=20`
- 当前实现：
  - 列表接口返回每封邮件的完整 `html_body`
  - 用户在列表中点击某封邮件时，前端直接从列表数据中的 `html_body` 渲染详情区域，不再单独请求详情接口
  - （注：当前最新实现已根据本方案完成优化，列表接口已不再返回 `html_body`，而是仅返回轻量字段与 `snippet`）

---

## 二、问题与目标

### 2.1 现有问题

1. **接口过重**
   - 列表接口返回完整 `html_body`，每页 20 封邮件，整体响应体积较大
   - 绝大部分邮件不会被真正点开，浪费带宽与后端序列化/反序列化开销

2. **前端渲染与内存压力**
   - 前端需要在内存中持有大量 `html_body` 字符串，影响页面滚动与交互性能
   - 对后续增加更多大字段（附件、解析结果、AI 摘要等）不友好

### 2.2 优化目标

1. **列表接口轻量化**
   - 列表仅返回必要的“概要信息”，不再返回完整邮件内容
2. **详情按需加载**
   - 用户点击某封邮件时，通过邮件 ID 调用“详情接口”获取 `html_body` 等大字段
3. **保持或提升用户体验**
   - 使用骨架屏等方式，保证点击邮件时的感知速度与顺滑度
4. **为后续扩展预留空间**
   - 更容易在详情接口中扩展附件、解析数据、AI 结果等大字段

---

## 三、目标方案总览

### 3.1 核心思路

1. **列表接口保留，字段精简**
   - 继续使用当前列表接口 URL 和分页参数
   - 去掉 `html_body` 等大字段，仅保留元数据 + 简短摘要 `snippet`

2. **增加/规范邮件详情接口**
   - 通过 `id` 获取单封邮件的完整内容，包括 `html_body`、`text_body`、附件等
   - 前端在点击邮件时调用该接口拉取数据并渲染详情

3. **前端交互调整**
   - 列表页只用轻量数据渲染
   - 点击某封邮件：
     - 立即在右侧或详情区域展示骨架屏
     - 并发起详情接口请求，返回后替换骨架屏为真实内容

---

## 四、接口设计方案（可实施）

### 4.1 列表接口（优化后）

**接口：**

- `GET /api/v1/emails`
- 参数（保持现状）：
  - `is_archived`: `boolean`
  - `is_deleted`: `boolean`
  - `page`: `number`
  - `page_size`: `number`

**请求示例：**

```http
GET /api/v1/emails?is_archived=false&is_deleted=false&page=1&page_size=20
```

**返回字段建议：**

每封邮件返回字段示例（去掉 `html_body`）：

```json
{
  "id": "email_123",
  "subject": "邮件标题",
  "from": "sender@example.com",
  "to": ["user@example.com"],
  "sent_at": "2025-11-14T10:00:00Z",
  "is_read": false,
  "is_archived": false,
  "is_deleted": false,
  "snippet": "这是从正文提取的前 100～200 字符纯文本摘要……"
}
```

说明：

- **必须字段**：`id`、`subject`、`from`、`to`、`sent_at`、`is_read` 等状态字段
- **推荐新增字段**：`snippet`
  - 后端从原 `html_body` 中去标签、截断，生成一个简短摘要
  - 列表显示正文预览时使用 `snippet`，不需要完整 HTML

> 列表接口整体响应结构（分页信息）可沿用现有格式，只是列表元素的字段精简。

---

### 4.2 详情接口

**接口：**

- `GET /api/v1/emails/{id}`

**请求示例：**

```http
GET /api/v1/emails/email_123
```

**返回字段建议：**

```json
{
  "id": "email_123",
  "subject": "邮件标题",
  "from": "sender@example.com",
  "to": ["user@example.com"],
  "cc": [],
  "bcc": [],
  "sent_at": "2025-11-14T10:00:00Z",
  "is_read": true,
  "html_body": "<html>...</html>",
  "text_body": "纯文本正文...",
  "attachments": [
    {
      "id": "att_1",
      "file_name": "report.pdf",
      "size": 123456
    }
  ]
}
```

说明：

- 详情接口可以包含：
  - 标题与基础元数据（方便直接使用，不必依赖列表缓存）
  - `html_body`：用于富文本渲染
  - `text_body`：用于搜索、高对比阅读或无 HTML 场景
  - `attachments`：附件列表（如有）
- 后续新增字段（例如解析后的结构化数据、AI 摘要等）优先放在详情接口中

---

## 五、前端交互与实现建议

### 5.1 列表页渲染

1. 支持分页、筛选、排序逻辑维持不变
2. 每一行显示：
   - 发件人 / 收件人
   - 标题
   - 发送时间
   - 已读/未读等状态
   - 正文预览使用 `snippet`（如有）

### 5.2 点击邮件查看详情

1. 用户在列表中点击一行邮件：
   - 将当前选中邮件 ID 保存在前端状态（例如 `selectedEmailId`）
   - 详情区域立即展示**骨架屏**

2. 前端调用详情接口：
   - `GET /api/v1/emails/{id}`
   - 拿到 `html_body` 后渲染详情内容

3. 错误与重试：
   - 接口请求失败时，在详情区域展示错误提示 + 重试按钮
   - 不影响列表页继续使用

### 5.3 可选优化：预取 & 缓存

1. **预取**（按需考虑）  
   - 若实际使用中发现用户几乎总是从上往下依次点开前几封邮件，可在列表加载完成后，对第 1～3 条邮件做延迟预取详情（不阻塞首屏渲染）。
   - 预取结果缓存在前端，当用户第一次点击时可直接用缓存数据，进一步提升速度。

2. **缓存**  
   - 单个会话内，如果同一封邮件被多次打开，可优先使用前端缓存的详情数据，避免重复请求。

## 六、兼容与迁移策略

1. **阶段 1：后端接口支持（已完成）**
   - 为列表接口添加 `snippet` 字段，并新增/开放 `GET /api/v1/emails/{id}` 详情接口
   - 过渡阶段列表接口曾保留 `html_body` 字段供旧前端继续使用（当前已移除）

2. **阶段 2：前端切换（已完成）**
   - 前端改造为：
     - 列表不再使用 `html_body`，只使用摘要和元信息
     - 点击邮件时调用详情接口获取 `html_body`，并使用骨架屏
   - 完成后验证列表首屏加载时间、接口体积等指标改善情况

3. **阶段 3：后端瘦身（已完成）**
   - 在确认前端不再依赖列表中的 `html_body` 后，后端从列表接口返回中彻底移除 `html_body`
   - 只保留概要字段与 `snippet`，实现真正轻量化

## 七、方案优劣对比（简表）

| 方案                         | 优点                                       | 缺点                         | 适用场景                     |
|------------------------------|--------------------------------------------|------------------------------|------------------------------|
| 现有方案：列表带 `html_body` | 打开详情无需额外请求，逻辑简单             | 接口过重、前端内存压力大     | 小规模、内容很短的系统       |
| 新方案：列表轻量 + 详情接口   | 列表轻量、扩展性好、资源利用更合理         | 打开详情多一次 HTTP 请求     | 正常邮件系统、内容较大的场景 |

> 推荐结论：采用“列表精简字段 + 详情按 ID 加载”的新方案，并在此基础上使用 `snippet`、骨架屏、缓存/预取等手段平衡性能与体验。
